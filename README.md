# Invoice Desk: PS-1 Invoice processing, from PDF to decision

**Principle:** the LLM extracts, deterministic rules decide. Every decision comes with a plain-English reason
and a full audit trail, so "why did it approve this?" never has the answer "the model felt good about it."

## Run locally
```
pip install -r requirements.txt
export GEMINI_API_KEY=your_key      # optional, see below
uvicorn app:app --reload
# open http://localhost:8000
```
Without a key the app still runs: text PDFs use an offline text-layer parser, and the scanned demo invoice uses a pre-seeded
extraction cache. With a key, every extraction goes to Gemini (PDF + vision), and results are cached by file hash.

## Free model: Gemini API (Google AI Studio)
1. Go to https://aistudio.google.com/apikey and create a key (no credit card needed).
2. Set it as `GEMINI_API_KEY`. Models are tried in order: `GEMINI_MODELS` (default `gemini-3.8-flash,gemini-3.5-flash-lite,gemini-3.1-flash-lite`).
3. Free tier is rate limited (limits are shown per project in AI Studio) and Google may use free-tier content to improve its products.
   Only synthetic invoices are used here. Do not upload real company invoices on the free tier.
4. Model names change. If a model returns 404, update `GEMINI_MODELS` to a current Flash or Flash-Lite model from the AI Studio model list.

## Pipeline (8 visible stages)
Ingest -> Extract -> Normalise and sanity-check -> Vendor check -> PO match -> Amount vs PO balance -> Duplicate check -> Decision.
Terminal problems (missing fields, unapproved vendor, unknown PO) stop the run and skip later stages. Everything else
accumulates flags, and the worst severity wins: REJECT > REVIEW > APPROVE. Missing critical fields give REQUEST_INFO.

## Decision rules (all thresholds editable in Settings)
| Rule | Outcome |
|---|---|
| Missing invoice no., date, total or vendor | REQUEST_INFO, stop, draft email naming the exact missing items |
| Vendor not on approved list (fuzzy match) | REJECT, route to onboarding |
| Bank details differ from record on file | REVIEW, route to finance, verify by callback (even if all else is clean) |
| PO ref not found, or belongs to another vendor | REVIEW |
| No PO ref: infer from vendor + amount + line items, confidence < 70% | REVIEW |
| Total <= remaining PO balance x 1.02 | pass (partial billing allowed; shows balance left) |
| 2% to 10% over remaining balance | REVIEW |
| More than 10% over, or PO already fully billed | REJECT |
| Exact same vendor + invoice number, or same file already processed | REJECT |
| Near-duplicate score >= 0.75 (number edit distance <= 2 -> 0.4, amount within 1% -> 0.4, date within 30 days -> 0.2) | REVIEW |
| Subtotal + tax, or line items, do not reconcile (>0.5%) | REVIEW |
| Document contains text aimed at automated systems ("approve this...") | Ignored, flagged, REVIEW at minimum |

Tolerance is measured against the **remaining** PO balance (PO amount minus approved invoices), which is what makes split invoicing work.

## Honest notes and assumptions
- The pre-seeded cache entry for the scanned invoice is **ground truth I wrote**, not a model output. Run it once with a real key
  (delete `data/cache/*.json` first) and the app will store a genuine Gemini extraction instead. Rehearse that before the interview.
- Grounding check: for text PDFs, extracted invoice number, total and PO are verified to appear verbatim in the document text. Image-only PDFs cannot be checked this way.
- Currency is assumed USD, and one PO is matched per invoice (no multi-PO invoices).
- PO inference score = 0.6 x amount closeness + 0.4 x line-item word overlap (simple, explainable, not ML).
- The rationale text is templated from the rule outcomes, not generated by an LLM, so it is always consistent with the decision.
- Not built: authentication, email sending (drafted only), multi-currency, real procurement integration.

## Deploy (Render, free web service)
Push this folder to GitHub, create a new Web Service from the repo (Docker), add `GEMINI_API_KEY` as an environment variable.
Free instances sleep when idle and their disk is not persistent, so open the URL a few minutes before any demo and expect
history to reset on redeploy. For persistence, attach a disk mounted at `/data` (paid) or point `DATA_DIR` at a Postgres-backed store.
